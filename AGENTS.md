# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the TypeScript flat-config factory, CLI helpers, and rule presets; add new rule sets under `src/configs/` and shared helpers in `src/utils.ts`.
- `bin/` publishes the CLI entry point, while `dist/` is generated by `pnpm build` and must remain read-only.
- `scripts/` hosts codegen tasks invoked through package scripts; `test/` and `fixtures/` provide the Vitest suite and sample projects for integration coverage.
- Root configs (`eslint.config.ts`, `tsconfig.json`, `tsdown.config.ts`) coordinate linting, compilation, and packaging—update them together when enabling new environments.

## Build, Test & Development Commands

- `pnpm install` installs catalog-pinned dependencies; avoid `npm` or `yarn` to keep lockfiles stable.
- `pnpm build` generates types and bundles to `dist/`; `pnpm watch` streams the same flow during development.
- `pnpm gen` refreshes generated enums and version metadata; run after touching `packages.json`-driven surfaces.
- `pnpm lint` checks the entire repo with this config; use `pnpm lint --fix` when iterating locally.
- `pnpm test` executes Vitest specs, and `pnpm typecheck` validates the TypeScript surface without emitting files.
- `pnpm dev` and `pnpm build:inspector` bootstrap the ESLint Config Inspector for interactive debugging.

## Coding Style & Naming Conventions

- Follow the enforced ESLint rules: 2-space indentation, single quotes, trailing commas, and no semicolons.
- Use ESM exports (`export const foo`) and keep rule collections alphabetised to satisfy `perfectionist` sorting.
- Name generated artifacts with a `*-generated.ts` suffix and keep file names in kebab- or flat lowercase (`factory.ts`, `globs.ts`).

## Testing Guidelines

- House new specs in `test/` using the `*.test.ts` pattern; pair broader scenarios with fixtures stored in `fixtures/`.
- Stick with Vitest `describe`/`it`; verify rule effects or CLI output with targeted assertions or snapshots.
- For filesystem-touching scripts, run `pnpm test --runInBand` to confirm deterministic execution before pushing.

## Commit & Pull Request Guidelines

- Follow Conventional Commits (`type: short summary`), mirroring existing history (`chore:`, `fix:`).
- Ensure `pnpm lint`, `pnpm test`, and `pnpm build` pass before opening a PR; note any local failures and their context.
- Reference related issues, summarise testing, and add screenshots when inspector-facing changes alter output.
